## 二、质量保障体系综述

项目在测试与工程治理上的投入显著高于普通毕设水平，核心特征：

1. **测试分层**：单元/纯逻辑（不联网）为主，叠加契约测试（SDD+TDD，spec 冻结于 .workbuddy/specs/，如 cache_ttl_contract 用可调时钟锁定 TTL 双检锁真实行为，声明"非与代码自洽的假绿"）、AST 静态守卫（93 文件直接解析源码固化架构不变量）、页面冒烟、后端安全回归。
2. **变异验证**：以契约 spec 末段实验形式存在（如 cache_ttl_contract spec 声明 mutation 实验），非独立变异测试框架（mutmut 等）全量运行——属"关键路径定点验证"而非系统性变异测试。
3. **工具链**：ruff（F/E/I/B/UP，渐进式引入、显式 exclude tests/scripts）、mypy（宽松：ignore_missing_imports、follow_imports=silent、exclude tests/）、pytest、uv.lock（单一依赖真理源，环境可复现）、coverage 数据文件存在。
4. **CI**：push/PR main 触发，仅跑确定性测试（6 个纯逻辑文件 + 后端安全回归 12/12），注释明确"避免 CI 因行情源波动变红"——工程取舍诚实，但覆盖面窄。
5. **文档体系**：docs/ 40+ 份（设计系统、财务契约、UI 审计、数据层健康监控×3、实证报告×12 等），README 含完整功能版图。
6. **工程治理记录**：R-01 except 静默吞错治理（63 处）、R-07 信号大文件瘦身、R-08 cache.db 体积审计、R-09 18 页惰性加载等，说明存在持续治理机制。

## 三、ISO 25010 八大质量特性评估

### 1. 功能适宜性（Functional Suitability）—— 4.5 / 5

**证据**：
- 74 个功能页面覆盖行情/决策/回测/情绪/事件/风险/自选/预警/模拟交易等完整链路；论文 1.3/3.3 给出功能拆解与模块映射。
- 5086 个测试用例含功能正确性断言；契约测试按 AC（验收准则）逐条锁定（cache_ttl_contract AC1–AC7）。
- 实证产物齐备：reports/ 下 backtest_decision_closure.json、market_regime.json、sentiment_predictive_power.json 等 12 份，回测结论（周期价差 22.8pt、避损 8.2pt 等）可复核。

**强项**：功能-测试-实证三层可追踪，功能交付密度高。
**弱项**：① 需求-测试显式追踪矩阵缺失（契约测试已隐含映射，但无一张表把需求条目对应到测试文件）；② 文档口径矛盾保留（3.3 节"15 个业务蓝图" vs 4.1/附录 D"13 个蓝图"）——属内容一致性风险。
**建议**：生成一张"需求条目 → 测试文件 → 实证报告"追踪表（可由现有契约测试 docstring 自动抽取）；统一蓝图计数。

### 2. 性能效率（Performance Efficiency）—— 3.5 / 5

**证据**：
- 多级缓存：本地 SQLite（cache.db）、TTL 双检锁契约测试锁定真实行为；R-09 18 页惰性 import 落地。
- 并发/超时护栏：共享池、整批超时、源级降级（论文 4.x）；R-08 对 cache.db 体积做过审计与策略。

**强项**：缓存与并发设计有契约测试兜底，性能风险被工程化管理。
**弱项**：无系统性性能基准——页面首屏、回测耗时、大样本查询无实测基线报告（component-benchmark.md 为早期雏形）；coverage/perf 数据未固化为门禁。
**建议**：对 4–6 个核心页面与回测流程建立可复跑的基准（pytest-benchmark 或独立脚本），把 P50/P95 写入报告与 CI。

### 3. 兼容性（Compatibility）—— 4 / 5

**证据**：
- 多数据源 4 级自动降级（AKShare → BaoStock → 新浪 → 东方财富 → 本地缓存），单点故障不崩；测试含 ssl_helper、ensure_proxy_ssl 契约（代理/SSL 兼容）。
- Python 3.10+/3.11+（README/pyproject 多版本表述并存）、CI 用 3.13；Docker 双镜像（backend + streamlit）、Windows 一键启动 + Linux CI 双平台。

**强项**：数据源兼容与部署形态兼容证据扎实。
**弱项**：浏览器兼容未系统测试（Streamlit 自管渲染）；跨平台主要在 Windows 验证，Linux 仅 CI 窄覆盖。
**建议**：在 README 明确 Python 版本矩阵（3.10/3.11/3.13 各自验证范围），避免口径漂移。

### 4. 易用性（Usability）—— 4 / 5

**证据**：
- 74 页面统一设计系统（docs/design_system.md）、暗夜/白天双主题、A 股红涨绿跌语义。
- UI 审计证据：docs/ui_audit_report.md、frontend-interaction-audit.md、ui_audit_baseline.json、ui-ds-pr-checklist.md。

**强项**：设计系统 + 审计基线闭环，易用性被当作一等质量属性管理。
**弱项**：无障碍（a11y）未评估；新手引导/首次使用路径（onboarding）未见专门设计与测试。
**建议**：补一份 a11y 清单（对比度/键盘可达性/读屏），对首次用户路径做 1 次任务走查。

### 5. 可靠性（Reliability）—— 4.5 / 5

**证据**：
- 5086 用例 + 93 个 AST 静态守卫（架构不变量可执行断言）+ 变异定点实验 + 缓存 TTL/代理 SSL 契约测试。
- 降级链（多数据源、源级降级）、健康监控文档（docs 三份 2026-11-02 数据层健康监控）、错误处理治理（R-01 63 处 except 治理）。
- 回测实证强调诚实负向结论（方向命中率 49.1%≈随机）——结论可靠性取向明确。

**强项**：防御纵深完整（测试分层 + 静态守卫 + 契约 + 降级 + 监控），"失败要有声音"的工程文化贯穿。
**弱项**：① CI 仅跑 6 个文件，全量回归依赖本地人工——单点故障（开发者环境）即无回归保障；② `@pytest.mark.live` 等自定义标记未在 pytest 配置注册（收集期告警，存在"标记拼写错误被静默忽略"的隐患）；③ 覆盖率未固化为门禁数字。
**建议**：CI 扩展为"全量不联网单测"（网络测试用 live/network mark 分离，已具雏形）；在 pyproject 注册 markers 消除告警；纯逻辑模块覆盖率 ≥80% 入门禁。

### 6. 安全性（Security）—— 4 / 5

**证据**：
- 后端安全回归 12/12 作为 CI 独立步骤（backend/tests/test_security）；JWT 认证契约（test_auth_jwt_contract）；论文 4.x 安全基线（JWT、SQLAlchemy 参数化防注入、密钥管理、CORS）。
- .env 隔离、权限契约测试存在。

**强项**：认证、注入防护、安全回归形成闭环，安全被纳入 CI 必跑项。
**弱项**：① 无依赖漏洞扫描（pip-audit / safety 未配置）；② CORS/CSRF 边界无独立审计文档；③ 密钥轮换策略未成文。
**建议**：CI 加 pip-audit；对 backend 做一次 CORS 来源白名单与 CSRF 复核并留档。

### 7. 可维护性（Maintainability）—— 4 / 5

**证据**：
- 分层架构（frontend / backend / modules / tests）与设计模式文档化（工厂/单例/策略/装饰器/降级链/统一信封）；论文 3.6/4.x。
- ruff/mypy 配置、uv.lock 单一依赖真理源（注释明确修复了"backend 依赖从未入库"的不可复现问题）、契约文档（finance_contract.md 等）、工程治理记录（R-01/07/08/09）。
- AST 静态守卫把架构不变量固化为可执行断言（6.5），变异实验验证守卫有效性（6.6）。

**强项**：架构有文档、有守卫、有治理记录，可维护性有制度性保障。
**弱项**：① tests/ 449 个文件平铺（未按模块分目录），定位成本高；② mypy 宽松配置（ignore_missing_imports、follow_imports=silent）使类型检查接近"名义存在"；③ ruff"渐进式、不强制全量通过"，存在历史例外（per-file-ignores 覆盖 quantagent/pages）。
**建议**：tests/ 按 modules/backend/pages 分目录迁移；mypy 对 backend 契约层与核心纯逻辑模块开严格模式；ruff 全量清零或形成已知例外清单（当前例外已注明，属可接受工程取舍）。

### 8. 可移植性（Portability）—— 4 / 5

**证据**：
- Docker Compose + 双 Dockerfile（backend/streamlit）；uv 一键还原可复现环境（.venv 独立于共享 venv）；requirements 双份（root + backend）。
- FastAPI 试点（backend_fastapi 9 端点）作为后端可迁移增量路线（docs/uv-fastapi-adoption.md）；Windows 一键启动脚本 + Linux CI。

**强项**：环境可复现与部署形态（本地/容器/CI）多路径并存，移植成本被显式管理。
**弱项**：① requirements.txt 与 pyproject.toml 双源并存（虽有单一真理源目标与注释，未完全收敛）；② 券商客户端依赖（QMT/easytrader）仅限本地、不可容器化，实盘路径移植受限；③ 无跨平台 CI 矩阵（Windows 侧仅本地验证）。
**建议**：以 pyproject.toml + uv.lock 为唯一依赖源，requirements.txt 改为生成物或删除；将 Windows 冒烟纳入 CI 矩阵（GitHub Actions windows-latest 至少跑核心单测）。
