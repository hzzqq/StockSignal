# P1 信号日常同步闭环（2026-11-04）

## 一句话

把「一次性跑 `scripts/refresh_p1_signals.py`」升级为**每天自动跑、跑完有体检、结论有快照、失败可追**的闭环；全部走仓库原生调度，**不依赖 `.workbuddy` 自动化框架**。

## 为什么做（此前缺什么）

| 缺口 | 事实 |
|---|---|
| 没有常跑入口 | `modules/p1_sync.py` 只有同步能力，`scripts/refresh_p1_signals.py` 只支持手跑 |
| 官方指引自认没入口 | `modules/data_health.py` 的 `p1_event` 刷新指引原文写着「本仓无刷新入口，需跨仓流水线触发」 |
| 副本「在」≠「新」 | 文件躺在 `data/p1_signals` 里看起来正常，但 `latest_date` 可能已停更多日，此前没有机器判定 |
| 失败不可见 | 同步被拒（全部候选无效）、写入失败只打日志，没有落档，事后无法复盘 |

## 交付物

| 文件 | 作用 |
|---|---|
| `modules/p1_sync_health.py` | 核心：`status_path()` / `assess_p1_sync_health()` / `run_sync_cycle()`（纯函数可测） |
| `backend/p1_sync_scheduler.py` | 守护线程：启动后等 45s 热身，之后每 `interval_minutes`（默认 60）跑一轮；单轮失败只留痕，循环不中断 |
| `scripts/p1_sync_daily.py` | CLI：`--once`（默认）/ `--status` / `--dry-run` / `--loop` / `--json`；退出码 0=ok、1=warn、2=dead |
| `tests/test_p1_sync_health.py` | 10 个守卫用例（dead/warn/ok、幂等、dry-run、全无效拒写、测试期不启线程） |
| `backend/app.py` | 接线：`start_p1_sync_scheduler(app)` 随后端启动（与其它调度器同一套 try/except 包裹） |
| `conftest.py` | 测试期默认 `STOCKSIGNAL_ENABLE_P1_SYNC_SCHEDULER=0`（沿用既有调度器隔离机制） |
| `modules/data_health.py` | `p1_event` 刷新指引改写成新入口（不再谎称「无刷新入口」） |

## 判定口径

一轮 = **同步 → 体检 → 落档**，三处判定都复用既有模块，不另造标准：

- **同步**：`modules.p1_sync.sync_once`（单向、幂等、绝不降级覆盖更新副本、全无效拒写）
- **结构**：`p1_sync.structural_ok`（**剥掉**「数据滞后」错误再判结构，避免把设计性滞后的 fusion 误报成损坏）
- **新鲜度**：`p1_signal_quality.summarize` 的 `freshness_ok` 与按模型 SLA（`DEFAULT_MAX_AGE_BY_MODEL`）
- **停摆**：只有 `mode=scheduler` 的快照才判，上次运行超过 **3 × 间隔** → 疑似停摆（CLI 手跑不计）

由此得到三态：

| 状态 | 条件 |
|---|---|
| `dead` | 副本目录不存在 / 无副本 / 全部副本结构不合格 |
| `warn` | 部分副本结构异常、或超出新鲜度 SLA、或调度器疑似停摆 |
| `ok` | 全部副本结构合格且新鲜度达标 |

本轮 `ok` 另要求**同步零错误**（`errors` 为空）——同步失败绝不被健康态掩盖。

## 运行方式

```powershell
# 跑一轮：同步 + 体检 + 写 data/p1_sync_status.json
python scripts/p1_sync_daily.py

# 只看健康（只读，不跑同步、不写盘）
python scripts/p1_sync_daily.py --status

# 只算计划不落盘（排查源/目标是否对齐）
python scripts/p1_sync_daily.py --dry-run

# 前台常驻（调试用）
python scripts/p1_sync_daily.py --loop --interval 60
```

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `STOCKSIGNAL_ENABLE_P1_SYNC_SCHEDULER` | `1`（开） | `0` 关守护线程；CLI 不受影响 |
| `STOCKSIGNAL_P1_SYNC_PUSH` | 关 | `1` 时**只在异常轮**推送（按自然日去重，未成功会如实留痕） |

## 已知边界（不粉饰）

1. **本仓只拉取、不生成**：P1-QuantFactor 侧不导出，同步就无法让数据变新（当前 19 天滞后需在 P1 侧重训导出后才会归零）。
2. **未接 UI 告警面**：异常目前落 `data/p1_sync_status.json` + 可选推送；接 94 页消息中心/数据健康页是后续项（`assess_p1_sync_health()` 一行即可调用）。
3. **推送默认关**：避免日常噪声；开启后只在异常轮推、按自然日去重。
4. **停摆判定只看调度器快照**：从未启动过调度器的机器不会报停摆（也就不会假报）。
5. **不含法定节假日口径**：新鲜度按自然日 SLA，与 `p1_signal_quality` 既有口径一致。

## 后续建议

1. 在数据健康页/消息中心接 `assess_p1_sync_health()`，让 `warn/dead` 进告警面（页面侧改动，需与 UI 收口批次协调）。
2. P1 侧恢复导出后跑一次 `python scripts/p1_sync_daily.py`，确认 `latest_date` 前移、`stale` 清零。
3. 若要「停更自愈」，需在 P1-QuantFactor 仓加流水线，不在本仓范围（本仓不越界回写 P1）。
