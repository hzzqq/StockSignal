# 缓存层有效性实证（T-273A）

> 毕设补充章节素材。数字全部来自 `reports/cache_layer_eval.json` 实验产物（脚本
> `scripts/bench_cache_layers.py`，固定 seed=20261013，可一键复现），**模拟负载、
> 非生产流量**——数据源全程 stub 零网络，此边界如实标注，不冒充线上数据。

## 1. 实验设计

StockSignal 的取数链路有四道缓存闸门：页面层 `st.cache_data`（TTL 分档）→ L0
进程内存 TTL-LRU（300s/600 条）→ L1 SQLite 落盘（`data/cache.db`，7 天）→ 四源
并行竞速失败后的 L5 陈旧兜底。观测埋点（T-272①）记录每层的命中/未命中。本实验
用受控负载回答三个问题：

1. 常规页面交互下，L0 内存层能拦截多少请求（即多少次交互**无需**触碰 SQLite 与网络）？
2. 进程重启（L0 清空）后，L1 落盘层的兜底能力如何？
3. 网络全断时，L5 兜底的「救回/诚实拒绝」分布如何？SWR（T-272④）在并发穿透下表现如何？

负载构成（场景 1，200 请求）：60% 重复交互（5 只热标的）、30% 轮询（20 只）、
10% 冷启动（50 只池）——近似真实页面「反复看几只 + 扫榜单 + 偶尔查新票」的行为。

## 2. 结果

### 2.1 L0 内存层：79.5% 请求未出进程

- 200 请求中 L0 命中 **159 次（hit_rate=0.795）**，未命中 41 次；
- 未命中的 41 次才进入 SQLite 读取与四源竞速（stub 层计数 164 = 41×4 源并行）；
- 全程耗时 0.43s（含 41 次竞速），若去掉 L0，等价于 200 次竞速 —— L0 把数据源
  层的请求压力削减到约 1/5。

### 2.2 L1 落盘层：进程重启后的 96% 兜底

- 主负载下 L1 命中为 0——这不是缺陷而是**容量语义的必然**：L0（600 条）未逐出时
  请求根本不会落到 L1；L1 的价值在进程重启场景。
- 「L0 重启模拟」（清空内存层等价重启）重放 25 个已落盘标的：L1 命中 **24/25
  （96%）**。唯一未命中经查系该标的在首轮负载中零请求（未落盘）——负载覆盖度的
  真实反映，重启后该标的走正常网络取数并回填 L1。

### 2.3 L5 陈旧兜底：50% 救回，50% 诚实拒绝

- 预填 3 个标的的 L1 后模拟四源全断：3 个有缓存的标的全部由 L5 兜底救回（陈旧
  数据必带 `as_of`/`is_stale` 标注）；3 个无缓存标的**宁可抛出明确错误，不喂碎片
  数据**（`min_rows=60` 行数下限 + 复权一致过滤）。
- 这一 3/3 分布是「诚实数据语义」的直接验证：缓存可以旧，但绝不能假。

### 2.4 SWR（stale-while-revalidate）：并发穿透下 100% 亚秒返回

- 16 线程并发打同一过期缓存键：**16/16 立即返回旧值**（带 `_swr_*` 标注），
  后台重建仅执行 **1 次**（单飞去重 93.8%）；
- 用户最大等待 p50=max=0.0s（fn 模拟耗时 0.3s；生产同路径 21 指标取数实测
  30–60s，按比例外推：同步语义下并发场景最后一个用户需等满一次完整取数，
  SWR 下全部亚秒返回）。

## 3. 结论与边界

- 四道闸门各司其职：L0 拦「重复交互」（79.5%），L1 兜「进程重启」（96%），
  L5 兜「网络全断」（有缓存救回/无缓存诚实拒绝），SWR 消「慢源阻塞」（100% 亚秒）。
- 诚实边界：本实验为固定 seed 的模拟负载，命中率数字依赖负载构成假设
  （60/30/10 混合）；生产流量的真实分布待上线观测积累后另行校准。
- 方法论上，本实验展示了「可观测埋点 → 受控实验 → 量化结论」的缓存设计验证
  闭环，可推广至其他工程子系统。
